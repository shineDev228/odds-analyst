## 1. Résumé exécutif

Le projet est **cohérent et sain**. Toutes les phases annoncées comme terminées
le sont réellement, le code correspond à la documentation, la chaîne de
vérification est verte de bout en bout et l'arbre Git était propre avant les
corrections documentaires du jour.

Trois écarts ont été corrigés dans ce rapport :

1. les en-têtes de statut des phases **3**, **7** et **7.1** indiquaient encore
   « implémentée — en attente de validation » alors que ces phases sont
   terminées (et remplacées, pour 3 et 7) ;
2. le critère d'acceptation n° 3 de la phase **14A** fixait un plafond de
   **200 requêtes** par passe, incompatible avec les **518 requêtes** réellement
   mesurées le 20/11/2026 ;
3. le tableau `phases` de `apps/web/src/messages/fr.ts` était du **code mort**
   (aucune référence), avec des statuts faux (« à venir » pour des phases
   livrées).

Un point d'exploitation reste ouvert et n'est **pas** un défaut de code : les
snapshots des **21 et 22/11/2026** n'ont pas été produits. La tâche du 22/11 a
échoué avec le code `0xC000013A` (interruption du processus) sans rien écrire.

## 5. Architecture

- **Monorepo** : `apps/api` (FastAPI + SQLAlchemy + Alembic), `apps/web`
  (Next.js App Router), `apps/api/engine` (moteur statistique pur, sans I/O),
  `infra/` (scripts PowerShell), `docs/`.
- **Séparation nette** : le moteur ne connaît ni la base ni le réseau ; les
  services orchestrent ; les routes exposent.
- **Source unique de données** depuis la phase 15 : BigBallsData. Les tables
  `provider_refs` et `connector_links`, les aperçus stockés et l'assistant de
  lien ont été supprimés.
- **Traçabilité** : chaque passe d'import écrit un `sync_runs` et la
  consommation dans `provider_usage`.
- **Snapshots** : les cotes sont figées deux fois par jour (`morning`,
  `evening`) pour permettre un backtest sans regarder le futur.

## 7. Exploitation

### Planification Windows

Deux déclencheurs quotidiens, en UTC : **05:30** (passe du matin) et **17:30**
(passe du soir). Options des tâches :

| Option | Valeur |
|---|---|
| `DisallowStartIfOnBatteries` | `false` |
| `StopIfGoingOnBatteries` | `false` |
| `StartWhenAvailable` | `true` |
| `StopOnIdleEnd` | `true` |
| `WakeToRun` | `false` |

### Constat du 21–22/11

- **Aucun snapshot** n'a été écrit le 21/11 ni le 22/11.
- La tâche du matin du 22/11 a été lancée à **15:12:12** (déclenchement
  différé par `StartWhenAvailable`) et s'est terminée avec le code
  **`0xC000013A`** sans rien écrire.
- Le compteur `provider_usage` du 22/11 (**70 requêtes**) provient
  probablement d'une passe du 21/11 à **23:29 UTC** ayant traversé minuit : il
  ne doit **pas** être lu comme une passe réussie le 22/11.
- Prochaines passes prévues : **soir du 22/11 à 17:30**, puis **matin du 23/11
  à 05:30**.

### Conséquence

Les snapshots des 21 et 22/11 sont **perdus et non reconstructibles** : un
snapshot doit être pris avant le coup d'envoi, on ne peut pas le recréer après.
Cela rend le critère d'acceptation n° 5 de la phase 14A (≥ 95 % des rencontres
terminées après 7 jours consécutifs) **non démontrable aujourd'hui**. Le
critère a été annoté en conséquence.

## 9. Recommandations

### Priorité haute

1. **Fiabiliser la tâche planifiée.** Le code `0xC000013A` signale une
   interruption brutale du processus. Vérifier l'historique complet de la tâche,
   puis ajouter une surveillance : une alerte (ou un simple fichier témoin) si
   aucune ligne `sync_runs` n'apparaît après chaque déclencheur.
2. **Documenter la perte des 21–22/11** dans le journal d'exploitation, pour ne
   pas la confondre plus tard avec un trou de données côté fournisseur.

### Priorité moyenne

3. **Rendre le critère 14A n° 5 mesurable** : calculer la complétude sur une
   fenêtre glissante de 7 jours effectivement observés, plutôt que sur 7 jours
   calendaires consécutifs.
4. **Compléter le bilan de la phase 15 dans le README** : les chiffres du
   README (2 314 rencontres, 145 équipes) datent du 18/11 ; la base compte
   désormais 2 322 rencontres et 146 équipes. Ce n'est pas faux — c'est un
   instantané daté — mais une phrase de mise à jour éviterait la confusion.

### Priorité basse

5. **Tracer la phase 14A.2 dans un commit dédié** ou ajouter une note dans son
   document expliquant qu'elle a été livrée avec la phase 15.
6. **Envisager un test de non-régression sur la planification** (lecture du
   fichier de tâche) pour détecter une option écrasée par une mise à jour de
   Windows.

## 10. Conclusion

Le dépôt est **prêt** : code, tests, typage, build et base sont cohérents, et
toutes les phases annoncées terminées le sont. Les corrections du jour alignent
la documentation sur la réalité et suppriment du code mort. Le seul risque
identifié est **opérationnel** — la fiabilité de la tâche planifiée — et non
fonctionnel. Il mérite une surveillance avant de tirer parti des snapshots pour
un backtest.
